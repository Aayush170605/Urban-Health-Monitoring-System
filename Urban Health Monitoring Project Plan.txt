1. BUILD REQUEST AND INTENDED RESULT

Create an attractive, simple browser application called "Urban Health
Monitoring System" for a teacher-facing college project demonstration.

The central feature must be a large, interactive, fictional city grid map with
exactly four monitoring locations. Each location displays simulated air
quality, particulate pollution, noise, traffic, and related environmental data.
Clicking a location reveals its readings, recent trends, and a transparent
Urban Stress Index. A presenter can change scenarios to demonstrate how the
same dashboard responds to changing conditions.

The finished app must be functional, visually polished, and easy to explain.
Opening it should immediately show the populated map. There is no login,
onboarding, configuration wizard, or empty dashboard to work through.

Use a fictional road layout. The location names come from the project, but
their positions, distances, road connections, and surroundings are invented
for the demonstration. Do not fetch geographic maps or use real coordinates.

All readings are synthetic. Display "Demo data" prominently in the header and
"Illustrative grid — positions are fictional" beneath the map. The app should
work without external services once its local dependencies are installed.

Implement the complete core experience described here. Future extensions in
Section 19 are explanatory context and are outside this build.

5. SYSTEM STRUCTURE AND DATA FLOW

Keep five clear parts inside the frontend:

1) Location catalogue
   Stores exactly four locations, their full names, grid coordinates, station
   labels, and descriptive context.

2) Demo data provider
   Stores baseline readings and generates repeatable history and future demo
   steps. Applies Baseline, Rush hour, and Improved conditions scenarios.

3) Analytics functions
   Derive AQI category, Urban Stress Index, display colours, active alerts,
   highest-reading location, and summary values from the current readings.

4) Shared application state
   Holds selected location, selected map layer, selected trend metric, current
   scenario, playback state, simulation time, current readings, and histories.

5) Presentation components
   Render the same data through the grid map, detail panel, trend chart,
   summary cards, alerts, and comparison table.

Data flow:

  Location catalogue + baseline fixtures + scenario + simulation step
       -> complete reading snapshot for all four locations
       -> pure analytics functions
       -> shared state / selectors
       -> map, details, trends, comparison, alerts, CSV

A user interaction changes state, and the affected views update together.
Never generate separate random values inside map markers or individual cards.
If a location has AQI 235, every current view of that location must show 235.

No network request is necessary for this flow. A small provider interface
creates a convenient replacement point if real data is added later. Do not
build a server merely to imitate this interface.


6. PARAMETERS AND WHAT THE USER SHOULD SEE

CORE AIR QUALITY

- AQI: unitless integer, 0–500, labelled "AQI (simulated)" in explanatory text.
  Show a category badge alongside its value.
- PM2.5: micrograms per cubic metre, display unit "µg/m³", one decimal at most.
- PM10: µg/m³, one decimal at most.
- CO: milligrams per cubic metre, display unit "mg/m³", one decimal.
  Keep its units distinct from particulate concentrations.

CORE NOISE

- Noise level: simulated LAeq over a 1-minute window, displayed in dB(A).
  Use the friendly label "Noise" with "LAeq, 1 min" in a tooltip or subtitle.
- Honk events: simulated event count per minute, displayed as events/min.

ADDITIONAL ACOUSTIC DETAIL

Show under an expandable "More readings" section, with brief definitions:

- SPL: instantaneous sound pressure level in dB(A).
- Lmax: maximum sound level within the simulated minute, dB(A).
- L10: level exceeded for 10% of the simulated minute, dB(A).
- L90: level exceeded for 90% of the simulated minute, dB(A).
- Loud-event count: optional extension, separate from honk count.
- Intermittency indicator: optional extension; no invented scientific formula
  is required for this prototype.

Use fixture values for these acoustic statistics. Do not claim that adding an
offset to LAeq computes real acoustic percentiles. Do not calculate LAeq by
arithmetically averaging decibel values. A genuine implementation needs the
appropriate measurements and aggregation method.

CORE TRAFFIC

- Vehicle count: vehicles observed during the simulated last minute.
- Traffic flow: veh/min. For the 1-minute count window it has the same numeric
  value as vehicle count, so show these as one combined reading.
- Mean vehicle speed: km/h, one decimal at most.
- Queue length: metres, integer.
- Average waiting time: seconds, integer.

WEATHER CONTEXT

- Temperature: °C, one decimal.
- Relative humidity: %, integer.
- Optional later fields: wind speed in m/s, wind direction, and rainfall.
  Do not display fabricated availability for these optional fields.

OTHER OPTIONAL AIR PARAMETERS

- NO2 and VOCs are possible extensions from the supporting document.
- Store unsupported optional readings as null and show "Not included in this
  demo" only in an expanded capability list. Do not render null as zero.
- A future VOC field must specify the compound or sensor output and its units.
  Do not assume a generic VOC number has a universal measurement unit.

CONTEXT AND DERIVED VALUES

- Timestamp, formatted in Asia/Kolkata (IST).
- Day, derived from the timestamp.
- Location ID, full name, grid position, and descriptive road context.
- Station label and explicit "Simulated source" status.
- Urban Stress Index: 0–100, derived using Section 11.
- Display category and alert reasons: derived from the current snapshot.

The main panel should foreground AQI, PM2.5, PM10, and noise. Keep the other
readings available without turning the first screen into a wall of numbers.

- Start advances one demo step every 5 seconds of real time.
- Each step advances simulated time by 5 minutes. Show "5 seconds = 5 simulated
  minutes" near playback controls or in a short help tooltip.
- Use deterministic smooth sequences with small changes around each scenario
  anchor. A seeded generator or deterministic curves are both acceptable.
- Pre-fill steps -12 through 0 as history. The final sample at step 0 must equal
  the scenario anchor exactly.
- Keep only the latest 13 samples per location in the visible 60-minute window.
- Samples contain the short-window readings described in Section 6, taken at
  5-minute sample times. Do not relabel a 1-minute count as a 5-minute total.
- A Step click advances exactly once while paused.
- Pause freezes data and simulated time. Selecting a location still works.

Enforce nonnegative concentrations, counts, speed, queue, and waiting time;

11. AQI, DISPLAY BANDS, AND URBAN STRESS INDEX

AQI CATEGORY LABELS

Use the Indian AQI categories, appropriate to the project's Bengaluru context:

  0–50     Good
  51–100   Satisfactory
  101–200  Moderate
  201–300  Poor
  301–400  Very Poor
  401–500  Severe

Use integer AQI values. Suggested interface colours: green, light green,
amber, orange, red, burgundy. Check text contrast on every badge. These colour
hex values are UI choices, not a claim to reproduce an official visual asset.

Category source: Central Pollution Control Board, About National Air Quality
Index. The source also explains pollutant sub-indices and averaging periods:
https://www.airquality.cpcb.gov.in/ccr_docs/About_AQI.pdf

Only the category boundaries are borrowed here. The app's AQI readings are
synthetic. Do not claim that this app produces official CPCB station readings.
Do not convert PM2.5 directly to AQI with a linear multiplier.

OTHER MAP DISPLAY BANDS

Use simple, explicitly labelled demo display bands:

Noise (dB(A)):
  Below 65 = Low; 65 to below 80 = Elevated; 80 or more = High.

PM2.5 (µg/m³):
  Up to 30 = Low; above 30 through 90 = Elevated; above 90 = High.

PM10 (µg/m³):
  Up to 50 = Low; above 50 through 150 = Elevated; above 150 = High.

Traffic, represented by queue length (m):
  Up to 75 = Low; above 75 through 150 = Elevated; above 150 = High.

Stress:
  Integer scores 0–39 = Low; 40–69 = Elevated; 70–100 = High.

Use green, amber, and red for these three-band displays, with the category
written beside the colour. Their legend must say "Demo display bands".
These are interface choices. They are not exposure limits, legal standards,
clinical boundaries, or declarations of safety. Do not derive legal noise
compliance from the prototype's short-window sound values.

URBAN STRESS INDEX FORMULA

The supplied project proposes the index but does not prescribe a formula.
Use this simple transparent demonstration formula:

  clamp01(x) = min(1, max(0, x))

  airScore   = 100 × clamp01(AQI / 300)
  noiseScore = 100 × clamp01((noiseLAeqDbA - 45) / (90 - 45))
  waitScore  = 100 × clamp01(waitingTimeSeconds / 180)
  queueScore = 100 × clamp01(queueLengthMetres / 300)

  trafficScore = 0.60 × waitScore + 0.40 × queueScore

  urbanStressIndex = round(
      0.45 × airScore
    + 0.35 × noiseScore
    + 0.20 × trafficScore
  )

The denominator 300 for AQI is a demo normalization reference, not the maximum
AQI. Values at or above 300 saturate the air component at 100. The noise,
waiting, and queue reference endpoints are also chosen for demonstration.

Use full precision for intermediate calculations and round only the final
score. The weights sum to 1. PM concentrations remain visible but are not
added again to this formula, which keeps the demonstration easy to explain.
Weather, CO, speed, and honking provide context and are not weighted inputs.

Baseline scores, rounded:
  Bagalur Cross: 60
  Phoenix Mall of Asia: 51
  Near Galleria Mall: 34
  Hebbal Flyover entry: 80

Example for Hebbal:
  Air component = 78.33
  Noise component = 82.22
  Traffic component = 78.00
  Weighted total = 79.63, displayed as 80/100, High

The score explanation should show component scores and weighted contributions,
plus: "Demo formula combining air, noise and traffic conditions. Not a
validated health or psychological assessment."

Name the interface metric "Urban Stress Index" and add a small "Demo" label.
Never call it a person's stress level, disease probability, or medical score.
If a required input is missing in future, return "Unavailable" rather than
substituting zero or silently changing the formula.

an audit log and notifications service are unnecessary.

Example at the baseline:
"Hebbal Flyover entry: AQI 235 (Poor), noise 82 dB(A), and demo stress 80/100."

All other locations have no alert under these rules at baseline. The summary
card therefore shows 1 location with alerts, even though Hebbal triggers three
rules. Recompute the list from the current snapshot after each change. Remove
a reason when its trigger clears. Remove the card when no reasons remain.

Use "Demo alert thresholds" in the alert area's help text. Do not imply that
a simulated notification was sent to an authority. Use a quiet inline message
such as "No active demo alerts" when the list is empty.

Optional explanatory copy can say "Compare the monitored locations" or
"This scenario illustrates higher local exposure indicators." Avoid health
diagnosis, actual travel advice, or claims that another route is safe.

19. FUTURE EXTENSIONS FOR EXPLANATION ONLY

The teacher may ask how this could become a real project. Explain the following
conceptual path; do not implement it for the demonstration:

- Sensor layer: suitable calibrated particulate, gas, weather, and acoustic
  instruments, with an ESP32 or Raspberry Pi serving as a possible gateway.
  A generic microphone or gas module alone should not be represented as a
  validated noise meter or concentration instrument.
- Traffic layer: manual counts or appropriately designed vision-based counts
  and speed/queue estimation. The current prototype uses no camera footage.
- Transport: HTTP or MQTT from devices to an ingestion service.
- Backend: a small Node.js or Python service for validation and aggregation.
- Storage: timestamped station readings in a database such as PostgreSQL.
- Analytics: official AQI computation using appropriate inputs and time
  windows, quality checks, missing-data handling, and field validation of the
  Urban Stress Index against a defined research objective.
- Interface: replace the demo provider while retaining the dashboard views.
- Later additions: real maps, supported extra pollutants, wind/rain context,
  predictive models evaluated on real data, water-quality monitoring, or
  appropriately governed aggregate disease-surveillance information.

These are architecture options, not a hardware shopping list or an assertion
that every sensor is suitable. The actual prototype ends at Section 18.
